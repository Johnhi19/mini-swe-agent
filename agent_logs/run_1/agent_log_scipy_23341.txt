Bug Report: zpk2tf unconditionally casts array-like gain k to int64, truncating fractional values
Description

When using scipy.signal.zpk2tf with a multi-dimensional array of zeros z and an array-like system gain k containing floating-point (fractional) numbers, the elements of k are 
unconditionally cast to xp.int64. This truncates non-integer values (e.g., 5.5 becomes 5) and completely breaks support for complex-valued gains in multi-row setups.

This regression was introduced while attempting to add Array API support for multi-dimensional inputs.

Root Cause Analysis

The bug resides within the newly modified multi-dimensional loop branch of zpk2tf.

Pre-PR Implementation:
The loop multiplied each row directly by the unmodified element of k, respecting its native floating-point or complex type:
Python
```
b[i] = k[i] * _pu.poly(z[i], xp=xp)
```

Post-PR Implementation:
An explicit, unconditional conversion to xp.int64 was added when isolating k_i for row-by-row iteration:
Python
```
k_i = xp.asarray(k[i], dtype=xp.int64)  # <-- HERE: Unconditional truncation
b[i, ...] = k_i * _pu.poly(z[i, ...], xp=xp)
```

While the early setup blocks in the PR contain appropriate guarding logic that only forces integer downcasting if xp.isdtype(k.dtype, 'integral') evaluates to true, this inner 
loop line ignores that safety mechanism. It forcefully coerces float-valued or complex-valued gains down into integers.
